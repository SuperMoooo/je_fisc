## 1. What this project is

A **Flutter** application targeting **iOS** and **Android** from a single Dart
codebase. Everything — screens, business rules, API calls — lives in `lib/`.
The `android/` and `ios/` folders are the native shells Flutter builds into;
you will only open them for signing, permissions and platform configuration.

The code follows **Clean Architecture**. That is one idea, applied per feature:

> Business rules must not depend on the things that come and go —
> the UI framework, the HTTP client, the database.

So each feature is split into three layers, and the dependencies only ever
point *inwards*, towards the rules:

| Layer | What lives there | May import |
|---|---|---|
| `domain` | Models (the one data type a feature has) and repository **interfaces** — the rules, and the promises the app makes | nothing but Dart and the `freezed` / `json_serializable` annotations |
| `data` | Datasources and the repository **implementations** | `domain` |
| `presentation` | Screens and the blocs that hold their state | `domain` |

```
presentation ─────► domain ◄───── data
     (UI)         (the rules)    (the world)
```

`presentation` never imports `data`. It asks the `domain` interface for what it
needs, and the wiring in `lib/config/di/` decides which implementation answers.
That indirection is what makes the data layer replaceable, and what makes the rules testable
without a device.

There is no separate entity: the **model** is the feature's one data type, so
every field is written once, and the repository hands the screens the same
class the API parsed. That is why a model carries JSON annotations from a
package rather than being plain Dart — the one concession `domain/` makes.

**Why it is worth the extra folders:** a screen that talks to Dio directly
cannot be tested without a network, cannot be reused when the endpoint changes,
and spreads error handling across the UI. Three folders up front avoid all
three.

### Generated, and still refreshable

The scaffold recorded a hash of every file it wrote in `.moarch.yaml`. That

## 2. Getting started

Do this once, in order. Steps 1 and 4 are the two people skip, and then spend
an afternoon on.

### Prerequisites

| You need | Why |
|---|---|
| Git | to clone the repository |
| Homebrew *or* the Dart SDK | only to install FVM, in step 1 |
| Xcode (macOS only) | to build and run on iOS |
| Android Studio | for the Android SDK and an emulator |

### 1. Install FVM, then the pinned Flutter

This project does not run on "whatever Flutter you happen to have". The exact
version is pinned in `.fvmrc`, and **FVM** (Flutter Version Manager) installs
and selects it.

```bash
# macOS / Linux
brew tap leoafarias/fvm && brew install fvm

# any platform, if you already have the Dart SDK
dart pub global activate fvm
```

Then, from the project root:

```bash
fvm install   # downloads the exact version .fvmrc names
fvm use       # links it into .fvm/flutter_sdk
```

From here on **every** Flutter and Dart command is prefixed with `fvm`:

```bash
fvm flutter --version   # this project's Flutter
flutter --version       # whatever is on your PATH — not necessarily the same
```

That prefix is the whole point. A build that works on your machine and fails in
CI is, more often than anything else, two different Flutter versions.
`.vscode/settings.json` already points the Dart extension at
`.fvm/flutter_sdk`, so once `fvm use` has run, F5, hot reload and the analyzer
use the pinned SDK too. `.fvm/` is gitignored, so a fresh clone has to run
`fvm use` once before that path exists.

### 2. Install the dependencies

```bash
fvm flutter pub get
```

### 3. Create your `.env`

Environment values are not committed. `.env.example` is — copy it and fill it
in:

```bash
cp .env.example .env      # Windows: copy .env.example .env
```

Fill in the keys it lists.

`.env` is gitignored; `.env.example` is not. Never put a real value in the
example file — add a blank key there whenever you add one to `.env`, so the
next person knows it exists at all.

### 4. Run code generation

Three things in this project are generated rather than written:
`lib/config/env/app_env.dart` compiles `.env` in through **envied**, and every
model gets its `.freezed.dart` and `.g.dart` from **freezed** and
**json_serializable**.

```bash
fvm dart run build_runner build --delete-conflicting-outputs
```

Run it again whenever `.env` changes, or whenever you add a field to a model. Until it has run once none of the generated halves exist and the
project will not analyze — which is why `.github/workflows` runs it before
`analyze` and before `test`.

The generated files are gitignored: they are one command away and a
regenerated file is a guaranteed merge conflict.

### 5. Run the app

```bash
fvm flutter devices        # what you can run on
fvm flutter run
```

In VS Code use **Run & Debug** instead — `.vscode/launch.json` already has the
configurations (`debug`, `profile`, `release`).

### When something goes wrong

| Symptom | Fix |
|---|---|
| `app_env.g.dart` not found, or `_$XModel` undefined | you skipped step 4 |
| A model's `toJson()` holds an object instead of a map | `build.yaml` is missing or lost its `explicit_to_json` |
| build_runner: "conflicting outputs" | re-run it with `--delete-conflicting-outputs` |
| iOS build fails on pods | `cd ios && pod install && cd ..` |
| The analyzer flags things `fvm flutter analyze` does not | run `fvm use`, then reload the window |
| Anything stale or inexplicable | `fvm flutter clean && fvm flutter pub get` |
| A generated file looks wrong | `moarch update --list`, then `moarch update <name>` |

At the root:

| Path | What it is |
|---|---|
| `pubspec.yaml` | Dependencies and the app version |
| `.fvmrc` | The pinned Flutter version — see section 2 |
| `.env` / `.env.example` | Environment values; the first is gitignored, the second is not |

Two rules keep those folders meaningful:

- **`core/` holds no feature logic, `shared/widgets/` holds no business logic.**
  If two features need it and it draws pixels, it is a shared widget; if it does
  not, it is in `core/`.
- **A widget composes into a screen; a view *is* one.** `shared/widgets/` holds
  the pieces, `shared/views/` the whole routes that answer to no feature — the
  same line `features/<name>/presentation/views/` already draws.
- **A feature never imports another feature's `data/` layer.** If two features
  need the same data, the repository belongs to whichever owns it, and the other
  depends on its `domain` interface.

## 5. How the architecture works

Follow one piece of data from the server to the screen. This is a `profile`
feature; every feature in `lib/features/` has the same shape.

### `domain/` — the rules

A **model** is the feature's one data type — what the screens draw, and the
payload as it comes over the wire:

```dart
// lib/features/profile/domain/models/profile_model.dart
@freezed
abstract class ProfileModel with _$ProfileModel {
  const ProfileModel._();

  const factory ProfileModel({
    required String id,
    required String name,
  }) = _ProfileModel;

  factory ProfileModel.fromJson(Map<String, dynamic> json) =>
      _$ProfileModelFromJson(json);
}
```

Freezed writes the constructor, `copyWith`, `==` and `hashCode` from that field
list, so equality covers **every** field — which is what the state layer runs
on. json_serializable writes `fromJson` / `toJson` from the same list, and
`build.yaml` renames every field to snake_case: `createdAt` reads and writes
`created_at` with no annotation. Only a key that is not snake_case needs saying
once, with `@JsonKey(name: 'createdAt')`.

There is no second class to keep in step. A field you add here is in the parsed
payload and on the screen, with no mapping in between. The other half of the
class is code-generated: after editing a model run

```bash
fvm dart run build_runner build --delete-conflicting-outputs
```

A **repository interface** is what the feature promises it can do — never how:

```dart
// lib/features/profile/domain/repositories/profile_repository.dart
abstract interface class ProfileRepository {
  Future<List<ProfileModel>> fetchAll();
}
```

Nothing under `domain/` imports Firebase or Flutter. That is the
point: these files can be tested with a plain `dart test`, and they survive
every change to the client and the UI.

### `data/` — the world

A **datasource** is where the bytes come from. A **repository implementation** puts
the datasources behind the interface and is the only class that satisfies it:

```dart
// lib/features/profile/data/repositories/profile_repository_impl.dart
class ProfileRepositoryImpl implements ProfileRepository {
  ProfileRepositoryImpl(this._remote);

  final ProfileRemoteDataSource _remote;

  @override
  Future<List<ProfileModel>> fetchAll() => _remote.fetchAll();
}
```

### The wiring: `lib/config/di/`

The locator knows both sides — which implementation answers which interface. It
uses **get_it**:

```dart
getIt.registerLazySingleton<ProfileRepository>(
  () => ProfileRepositoryImpl(getIt<ProfileRemoteDataSource>()),
);
```

Anywhere else in the app, `getIt<ProfileRepository>()` hands back that instance
— and the caller only ever sees the interface type.

- `registerLazySingleton` — built on first use, one instance for the app's life.
  The default for repositories and services.
- `registerFactory` — a new instance every call.

The registrations are one file per layer, so none of them grows with the app:

| file | holds |
| --- | --- |
| `injector.dart` | `getIt`, and `setupInjector()` calling the registrars below. Nothing else. |
| `external_module.dart` | The instances that are not ours: the HTTP client, the Firebase handles, the platform keystore. |
| `core_module.dart` | The services under `lib/core` — permissions, media, notifications. |
| `data_module.dart` | Datasources and repositories, one block per feature. |
| `presentation_module.dart` | The blocs. |

`setupInjector()` calls them in that order, but the order is a readability
choice: every registration is lazy, so a layer may depend on one registered
after it.

> ⚠️ `data_module.dart` and `presentation_module.dart` each contain a
> `// moarch:registrations` comment. `moarch create feature` inserts new
> registrations directly above them. Keep the lines where they are or the
> tooling has nothing to anchor to.

### Errors: exactly one type reaches the UI

Everything that can fail is funnelled into `AppException`
(`lib/core/errors/app_exception.dart`). A widget never sees a
`DioException`, a `FirebaseException` or a `SocketException` — it sees an
`AppException` with a `message` written for a person.

```dart
// ✅ the data layer translates, the UI displays
try {
  final profiles = await repository.fetchAll();
  // …
} on AppException catch (e) {
  // e.message is safe to show
}

// ❌ never
try {
  // …
} catch (_) {}                       // a swallowed error is a bug you cannot find
catch (e) { showDialog(text: '$e'); }  // stack traces are not user-facing
```

`AppException` is sealed, so the kinds below it — `NetworkException`,
`ServerException`, `NotFoundException`, `AuthException`, `CancelledException`,
`UnknownException` — are the whole list, and a `switch` over one is checked for
completeness. Catch the base class wherever all you do is show `message`, which
is most places. Catch a subclass where one failure needs a path of its own:

```dart
try {
  await repository.refresh();
} on NetworkException {
  // offline says nothing about the session — keep it
} on AppException catch (e) {
  // everything else: e.message is safe to show
}
```

Two rules follow from that, and section 11 repeats them because they are the
ones most often broken:

1. **Never leave a `catch` empty.** Log it or handle it.
2. **Never show a raw error.** Show `AppException.message`.

## 6. State management — Bloc

Screens do not hold their own state. Each feature has a **bloc**: it receives
**events** and emits **states**. The screen sends events and rebuilds on states.
Nothing else moves between them.

### The events

A sealed family in `presentation/blocs/profile_event.dart`:

```dart
sealed class ProfileEvent extends Equatable {
  const ProfileEvent();

  @override
  List<Object?> get props => const [];
}

final class ProfileStarted extends ProfileEvent {
  const ProfileStarted();
}
```

One event is what `moarch create feature` generates. A refresh and a retry are
the same load, so they dispatch `ProfileStarted` again rather than each getting
an event of their own. Add one per *action* the screen takes — a delete, a
submit — not one per way of asking for the same thing.

### The state

**One class per screen**, with the phase as a field. What it carries beyond
the status is your screen's business:

```dart
// core/utils/app_status.dart — shared by every screen
enum AppStatus { initial, loading, success, failure }

class ProfileState extends Equatable implements StatusState<ProfileState> {
  const ProfileState({
    this.status = AppStatus.initial,
    this.errorMessage,
    this.successMessage,
    this.items = const [],           // ← you add this
  });

  static const placeholder = ProfileState(status: AppStatus.success);

  final AppStatus status;
  final String? errorMessage;
  final String? successMessage;
  final List<ProfileModel> items;

  ProfileState copyWith({...}) => ...;

  @override
  ProfileState withStatus(AppStatus status, {String? errorMessage}) =>
      copyWith(status: status, errorMessage: errorMessage);

  @override
  List<Object?> get props => [status, errorMessage, successMessage, items];
}
```

One class rather than a sealed state per phase, because the data outlives the
phase. A screen that keeps its list on screen while a save runs leaves the
status on `success` and emits the new data when it lands — with a state class
per phase, that list has to be declared on every phase that can show it, and
the view ends up with a `_body` per shape. Here every status hands the view the
same `ProfileState`.

The status itself is shared (`core/utils/app_status.dart`) rather than declared
per feature, because `AppStatusView` below switches over it — a widget cannot
switch over a type it does not know. A phase that belongs to one screen alone
is a field on that screen's state, not a value on the enum.

`errorMessage` and `successMessage` are **one-shot**: `copyWith` drops them
unless they are passed again, so the state that sets one is the only state that
carries it and a toast fires once instead of on every rebuild. An action that
fails without blanking the screen is
`copyWith(errorMessage: e.message)` with the status left on `success`.

**Equatable is not decoration here.** Bloc drops an `emit` whose state equals
the current one, and `BlocBuilder` rebuilds on the same test. A field left out
of `props` makes two different states compare equal, and the second emit is
dropped — so a new field has to reach four places: the constructor, `copyWith`,
`props`, and `placeholder` (the fake data the loading skeleton is traced from).

### The bloc

```dart
class ProfileBloc extends Bloc<ProfileEvent, ProfileState>
    with ActionBlocMixin<ProfileEvent, ProfileState> {
  ProfileBloc(this._repo) : super(const ProfileState()) {
    on<ProfileStarted>(_onStarted);
    on<ProfileRenamed>(_onRenamed);
  }

  final ProfileRepository _repo;

  Future<void> _onStarted(
    ProfileStarted event,
    Emitter<ProfileState> emit,
  ) =>
      runAction(emit, (current) async {
        final items = await _repo.fetchAll();
        return current.copyWith(status: AppStatus.success, items: items);
      });

  Future<void> _onRenamed(
    ProfileRenamed event,
    Emitter<ProfileState> emit,
  ) =>
      runAction(emit, (current) async {
        await _repo.rename(event.id, event.name);
        return current.copyWith(successMessage: 'Saved');
      });
}
```

- **`runAction` is every handler.** It comes from `ActionBlocMixin`
  (`lib/core/utils/app_status.dart`) and handles loading, `AppException` and
  unknown errors for you. It hands you the state as it was before the handler;
  return the state that should follow. Where the screen already is decides
  what a failure looks like: with nothing on screen yet it emits `loading`
  first and lands on `failure` (the error screen); over data already on screen
  it emits no `loading` and keeps `success`, setting only `errorMessage` — a
  toast, not a blank screen. The first load returns
  `status: AppStatus.success` itself; later actions inherit it from `current`.
- The repository is a constructor parameter, so a test hands it a fake. The
  locator is what fills it in, in `presentation_module.dart`:
  `getIt.registerFactory<ProfileBloc>(() => ProfileBloc(getIt<ProfileRepository>()))`.
- `emit` is only valid inside a handler, and only while it is still running.
  Emitting after an `await` that outlived the handler throws.
- Blocs import `package:bloc/bloc.dart`, not `flutter_bloc` — they stay pure
  Dart, which is what the `avoid_flutter_imports` rule keeps true.

### Using it in a widget

The **page** provides the bloc; the **view** draws it:

```dart
class ProfilePage extends StatelessWidget {
  const ProfilePage({super.key});

  @override
  Widget build(BuildContext context) => BlocProvider(
        create: (_) => getIt<ProfileBloc>()..add(const ProfileStarted()),
        child: const ProfileView(),
      );
}
```

```dart
BlocBuilder<ProfileBloc, ProfileState>(
  builder: (context, state) => AppStatusView(
    status: state.status,
    message: state.errorMessage,
    onRetry: () => context.read<ProfileBloc>().add(const ProfileStarted()),
    isEmpty: state.items.isEmpty,
    skeleton: (context) => _body(context, ProfileState.placeholder),
    builder: (context) => _body(context, state),
  ),
)

// Handed the whole state, whatever the status — so a phase that draws over
// data already loaded needs nothing extra here.
Widget _body(BuildContext context, ProfileState state) => ListView(
      children: [for (final item in state.items) Text(item.name)],
    );
```

`AppStatusView` (`shared/widgets/app_status_view.dart`) owns the three shells
every screen has — the skeleton, the failure screen and the empty state — so
the view names only its body. Written out by hand that is the same `switch`
in every feature you will ever scaffold:

```dart
// what AppStatusView does for you
switch (state.status) {
  AppStatus.initial || AppStatus.loading =>
    Skeletonizer(child: _body(context, ProfileState.placeholder)),
  AppStatus.failure => ErrorView(message: state.errorMessage, onRetry: ...),
  AppStatus.success when state.items.isEmpty => const EmptyView(),
  AppStatus.success => _body(context, state),
}
```

> ⚠️ A **refresh** should not set `AppStatus.loading` — that trades the body
> for a skeleton and the screen flickers. Leave it on `success` and emit the
> new data when it arrives; the old data is still on the state to draw.

The one-shot messages go through the listener half:

```dart
BlocConsumer<ProfileBloc, ProfileState>(
  listenWhen: (previous, current) =>
      previous.errorMessage != current.errorMessage ||
      previous.successMessage != current.successMessage,
  listener: (context, state) {
    final error = state.errorMessage;
    if (error != null) AppToast.error(context, error);

    final success = state.successMessage;
    if (success != null) AppToast.success(context, success);
  },
  builder: ...,
)
```

| You want to | Use |
|---|---|
| rebuild on new state | `BlocBuilder` |
| side effect only (snackbar, navigation) | `BlocListener` |
| both at once | `BlocConsumer` |
| send an event | `context.read<ProfileBloc>().add(const ProfileStarted())` |
| read the current state without rebuilding | `context.read<ProfileBloc>().state` |

> ⚠️ `context.watch` belongs in `build`, `context.read` in callbacks — never
> the other way round.

On top of the analyzer, the bloc team's own rules run separately:

```bash
dart pub global activate bloc_tools
bloc lint .
```

They cover file naming, Flutter imports inside a bloc, and public fields on a
state. The ruleset is in `analysis_options.yaml`.

## 7. Adding a feature

The layers are regular enough to generate. From the project root:

```bash
moarch create feature profile
```

That scaffolds `lib/features/profile/` with the layers you tick, registers the
repository in `data_module.dart` above the `// moarch:registrations` anchor
(and the bloc in `presentation_module.dart`, above its own), and
generates the presentation layer in this project's stack:
the bloc, its sealed event and state families, and the page that provides
it to the widget tree.

Then the part that is yours:

1. **Describe the data.** Fields on `profile_model.dart`; `fromJson` / `toJson`
   come with them from json_serializable.
2. **Say what the feature can do.** Methods on the repository *interface*,
   implemented in `profile_repository_impl.dart`, with the actual call in the
   datasource.
3. **Hold the screen's state.** Add the fields to `profile_state.dart`
   (and to `copyWith`, `props` and `placeholder`), add an event to
   `profile_event.dart`, register it with `on<ProfileSomething>(...)` in the
   bloc's constructor, and wrap the handler's body in `runAction` so loading
   and errors are handled for you.
4. **Draw it.** Build the view out of `lib/shared/widgets/` rather than raw
   Material widgets — the kit is catalogued in `docs/UI_KIT.md`.
5. **Route to it.** Add the path to `lib/config/router/app_routes.dart` and
   the route to `app_router.dart`.

### The other generators

| Command | What it does |
|---|---|
| `moarch create feature <name>` | A whole feature, layers selectable |
| `moarch create model <feature> <name>` | A model inside an existing feature (`--from-json` infers its fields from a sample) |
| `moarch create bloc <feature> <name>` | Another state + event + bloc trio |
| `moarch create scope <feature> <name>` | Carries a screen's blocs to the routes, sheets and dialogs it opens |
| `moarch create widget <name>` | A widget from the kit (`docs/UI_KIT.md`) |
| `moarch create empty-factories [feature]` | Injects `.empty()` factories into every model |
| `moarch create tests [feature]` | Unit tests for every state holder, integration tests for every GET endpoint |
| `moarch create theme` | Switches the project between one theme and light + dark |
| `moarch create flavors [names…]` | See section 8 |
| `moarch update --list` | Which generated files are out of date, and which you have edited |
| `moarch doctor` | Checks the project for known problems (`--fix` applies what it can) |

### Tests

Tests live in `test/unit/` and `test/integration/`:

```bash
fvm flutter test
```

The scaffold ships no tests of its own beyond the smoke test. Once a
feature has real methods, generate them from the code:

## 8. Flavors & environments

A **flavor** is the same codebase built as a different app: its own display
name, its own application id / bundle id, its own backend. That is what lets a
`dev` and a `prod` build of je_fisc sit on one device at the same time
instead of overwriting each other.

This project does **not** have flavors yet. Add them the day it needs more
than one environment installed at a time:

```bash
moarch create flavors dev staging prod
fvm flutter pub get
dart run flutter_flavorizr
```

Review the app names and ids in the generated `flavorizr.yaml` before running
the second command. Until then `fvm flutter run` builds the single app, and
per-environment values come from `.env` (section 2, step 3).

### How it is put together

[**flutter_flavorizr**](https://pub.dev/packages/flutter_flavorizr) owns the
native side. `flavorizr.yaml` declares the flavors; `dart run flutter_flavorizr`
writes them into:

- `android/app/build.gradle(.kts)` — the `productFlavors` block
- `android/app/src/main/AndroidManifest.xml`
- the iOS xcconfigs, `Info.plist` and the Xcode schemes
- `lib/flavors.dart` — the Dart side

**There is only one `main.dart`.** No `main_dev.dart` / `main_prod.dart`: the
`instructions` list in `flavorizr.yaml` runs the native processors and the
Dart-side generator only, and never touches the entry point. Read the current
flavor off the generated `lib/flavors.dart` (`F.appFlavor`, `F.name`,
`F.title`) wherever behaviour has to differ.

To add or rename a flavor, edit `flavorizr.yaml` and re-run
`dart run flutter_flavorizr`.

### What catches people out

- **Suffixed ids.** Every non-production flavor gets its id suffixed
  (`com.example.app.dev`). That suffix is exactly what makes side-by-side
  installs possible — do not "tidy" it away.
- **`.vscode/launch.json`** already carries flavored entries. They fail with
  "Could not find product flavor" / "does not define custom schemes" until
  flavorizr has actually run.
- **CI passes `--flavor` too.** A flavored project needs the flag added to the
  build workflows, or the runner builds the unflavored target and fails.
- **Flavors are not `.env`.** Flavors change *which app* is built; `.env`
  changes *the values it is built with*. Most projects need both.

## 10. CI/CD & GitHub secrets

Four workflows live in `.github/workflows/`:

| Workflow | File | Runs on | What it does |
|---|---|---|---|
| CI | `unified_workflow.yml` | push to `main`/`develop`, PRs to `main` | format, analyze, test, build |
| CSA | `csa.yml` | push and manual | code scanning: SAST, secret scan, SBOM, licence report |
| Build IOS IPA | `build_ipa.yml` | manual | signs and builds the IPA, uploaded as the `release-ipa` artifact |
| Build ANDROID APK | `build_apk.yml` | manual | signs and builds the APK, uploaded as the `release-apk` artifact |

"Manual" means **Actions → the workflow → Run workflow**. Both build workflows
check for their secrets first and **skip cleanly** when they are missing, rather
than failing — so a fresh clone or a fork stays green until signing is set up.

### The secrets

Repository → **Settings → Secrets and variables → Actions**.

| Secret | Used by | Value |
|---|---|---|
| `BASE_URL` | all workflows | the API base URL compiled into the build |
| `IOS_P12_BASE64` | `build_ipa` | base64 of your `.p12` (certificate + private key) |
| `IOS_P12_PASSWORD` | `build_ipa` | the password you set when exporting the `.p12` |
| `IOS_PROVISIONING_PROFILE_BASE64` | `build_ipa` | base64 of your `.mobileprovision` |
| `IOS_TEAM_ID` | `build_ipa` | your Apple Developer Team ID |
| `ANDROID_KEYSTORE_BASE64` | `build_apk` | base64 of your `.jks` keystore |
| `KEYSTORE_STORE_PASSWORD` | `build_apk` | the keystore's store password |
| `KEYSTORE_KEY_PASSWORD` | `build_apk` | the key's password |
| `KEYSTORE_KEY_ALIAS` | `build_apk` | the key alias, e.g. `my-key-alias` |

**Why base64?** A GitHub secret holds text, and a `.p12`, a `.mobileprovision`
and a `.jks` are binary files. Base64 is how a binary becomes a secret: the
workflow decodes it back into a file on the runner, imports it into a temporary
keychain, and that keychain dies with the job.

### Where the step-by-step lives

- **`docs/STEPS_FOR_WORKFLOW.md`** — every secret in the table, produced from
  scratch. The iOS half walks through generating the private key, the signing
  request, converting Apple's `.cer`, bundling the `.p12` and creating the
  provisioning profile **with OpenSSL, so no Mac is needed**, and ends with the
  exact PowerShell one-liners that base64 the `.p12` and the
  `.mobileprovision`.
- **`docs/GENERATE_JKS_FILE.md`** — the Android release keystore and its
  base64.

> 🔐 The `.p12`, the `.mobileprovision` and the `.jks` are **never** committed.
> They belong in the password manager and in GitHub secrets, nowhere else.

## 11. Code standards

### Naming

| Element | Convention | Example |
|---|---|---|
| Files and folders | `snake_case` | `profile_view.dart` |
| Classes, enums, extensions | `PascalCase` | `ProfileBloc` |
| Variables and methods | `camelCase` | `fetchProfile()` |
| Private members | leading `_` | `_repo`, `_onSaved` |
| Constants | `camelCase` | `defaultPadding` |

### Widgets

- **Small and reusable beats one long `build`.** When a `build` method grows a
  section, extract it as a widget class, not as a `Widget _buildHeader()`
  method. A class gets its own `const` constructor and its own rebuild
  boundary; a method is rebuilt with its parent every time.
- **Every widget gets its own file.** The class is public and lives in the
  feature's `presentation/widgets/` (`profile_header.dart` → `ProfileHeader`),
  never as a private `_ProfileHeader` at the bottom of the view. A widget a
  second feature needs moves to `lib/shared/widgets/`.
- **`const` wherever it compiles.** A `const` widget is skipped entirely on
  rebuild.

```dart
const AppButton(label: 'Save');   // ✅
AppButton(label: 'Save');         // ❌ when it could have been const
```

- **Reach for `lib/shared/widgets/` before Material.** The kit is catalogued in
  `docs/UI_KIT.md`, and `moarch create widget <name>` adds one on demand.

### Errors

- Never leave a `catch` empty — log it or handle it. A swallowed exception is a
  bug nobody can find.
- Never show a raw error or a stack trace in the UI. Catch `AppException` and
  show its `message`.
- Translate at the boundary: the datasource turns transport errors into
  `AppException`, so the UI has one type to handle. Section 5 has the pattern.

### Before every commit

```bash
fvm dart format .
fvm flutter analyze
fvm flutter test
```

The CI workflow checks formatting, runs the analyzer and runs the tests, and
fails the build on any of them — so running all three locally only ever saves a
round trip. The rules themselves are in `analysis_options.yaml`.

`bloc lint .` is separate: the bloc team's ruleset is not part of CI, and
section 6 has the one-time setup it needs.
